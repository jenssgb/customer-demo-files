ON-CALL INCIDENT NOTES — INC-2026-0521-001
Nexova Platform — Production Incident
Date: May 21, 2026 | Time: ~04:17 UTC

=== PRIYA KAPOOR (Lead SRE) ===

04:19 — Got paged. Dashboard alerts already lit up. DB connection pool at 98% in eu-west.
Checked Datadog first — API error rate spiking hard, 23%. Not a deploy. Last deploy was May 19 (analytics v2.3.1).

04:22 — SSH'd into prod-db-eu-01. Running `SHOW PROCESSLIST` — saw 180+ connections all from one process: "monthly_active_user_export_enterprise". ALL in status "executing", some had been running for 30+ minutes. This is NOT normal. That job should never hold more than 20 connections.

04:27 — Pulled the job config. Analytics export v2.3.1. Found the bug immediately — connection_limit param is just *gone* from the config. Someone removed it in the migration script. The job was spinning up as many connections as it needed with no cap.

04:28 — Tried to kill the job. Cron respawned it before the kill finished. Classic.

04:29 — Called Marcus to disable the cron scheduler while I killed the process manually. Took two attempts. Pool started draining.

04:32 — Pool below 72%. Error rates started dropping across all three regions in sequence — EMEA first, then AMER, then APAC. Makes sense given where the DB primary is.

04:39 — Confirmed root cause: analytics v2.3.1 PR (#4798, merged May 19) — config schema migration script dropped the connection_limit field. Nobody caught it in review because the job still ran successfully in staging (staging DB has unlimited connections in test env). No canary deploy for analytics jobs.

05:00 — Opened extended monitoring window. Wanted to make sure the pool stayed stable and we didn't see secondary effects (cache warming, delayed queue processing).

Key observation: We didn't have a 75% pool utilization alert — we only alert at 95%. By the time we got paged, we were already at 98% and cascading. That's too late. Need early warning.

What went wrong in process: 
- No connection_limit validation in CI/CD pipeline
- Staging environment doesn't enforce connection limits (different from prod)
- Analytics job changes not flagged as "risky" in PR template
- Alert threshold too late (95% instead of 75%)

Personal note: This is the second time in 6 months we've had an unguarded scheduled job cause a cascade. After the batch processor incident in November, we said we'd add db-config linting to CI. That PR has been sitting for 3 months. We need to actually ship it.
